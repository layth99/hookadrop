# Product Deduplication Fix for HookaDrop

The fix eliminates duplicate products in the Android app by preventing the merge of static fallback products (from `DataProvider.kt`) with live database products. The database was already clean (0 duplicates), confirming the root cause was client-side display logic, not server-side data integrity. Backend defenses were added to prevent future database-level duplicates through unique indexes and duplicate checks in the product creation API.

**Watch for:** (confirmed) Android ProductSyncManager still includes commented fallback merge logic that could be re-enabled accidentally. (likely) Unique index may fail if products.json legacy seed data contains duplicates. (confirmed) Dashboard duplicate check runs on every create attempt even when the product name is unique, adding latency.

**Verdict**: APPROVED

---

## High-level view

The Android app was merging 35 hardcoded static products from `DataProvider.kt` (IDs like "p3", "p11") with database products (ObjectIds like "6ac476d12295b5e5450ad47b"). Since IDs never matched, both versions appeared in the UI. The fix changes `ProductSyncManager.kt` to stop merging static products when database products exist — static products now only appear as offline fallback when the backend is completely unreachable.

The backend adds three layers of duplicate prevention: a compound unique index on (name, category), a duplicate check in the `createProduct` controller that returns 409 Conflict, and improved duplicate detection in the seed script. The database diagnostic confirmed 0 existing duplicates, so no cleanup was needed.

The dashboard adds a pre-submit duplicate check that prompts the admin to edit the existing product instead of creating a duplicate.

The seed script now normalizes product names (collapsing whitespace) and checks both name and category when determining if a product already exists, making it safe to run multiple times.

## Android ProductSyncManager merge elimination

**File:** `hookaDrop App/HookahDrop/app/src/main/java/com/hookahdrop/app/data/ProductSyncManager.kt`

The root cause was in the `sync()` function (lines 139-167). The original logic merged static products from `DataProvider.kt` with database products by product ID:

```kotlin
// Old logic (removed):
DataProvider.products.forEach { staticProduct ->
    if (!freshMap.containsKey(staticProduct.id)) {
        freshMap[staticProduct.id] = staticProduct
    }
}
```

Static products have IDs like "p3", "p11". Database products have MongoDB ObjectIds. The IDs never match, so both versions were added to the map. Result: Tobacco category showed 10 products (5 from DB with IDs like "6ac476d12295b5e5450ad47b" + 5 static with IDs like "p3", "p11", "p12", "p13", "p14").

The fix (lines 148-157) replaces the merge with a conditional: static products are only added when the database returns zero products (offline mode). When the backend is reachable and returns any products, only database products are displayed:

```kotlin
// Only merge static products if the database is completely empty (offline mode)
// If we have any DB products, they are the source of truth
// Static products should NOT be displayed alongside live data

productMap.clear()
productMap.putAll(freshMap)  // Only DB products
```

The commented code immediately below (lines 148-152) shows the old merge logic. Remove entirely — leaving it as a comment invites accidental re-enablement.

The offline fallback is preserved in `getAllProducts()` (lines 60-63): if `productMap.isEmpty()` after sync, static products are returned.

## Backend unique index on (name, category)

**File:** `models/Product.js`

Line 19 adds a compound unique index:

```js
productSchema.index({ name: 1, category: 1 }, { unique: true });
```

The index is created when the model is first loaded (typically on server startup). If duplicate products already exist in the database, index creation fails and the server may not start. The diagnostic confirmed 0 duplicates exist, so this is not a concern for the current deployment. However, if the legacy `products.json` file (35 products with IDs "p1"–"p35") is imported manually, duplicates could be introduced.

The unique index is case-sensitive by default. Product names "Ways 200 Grammes" and "ways 200 grammes" would be treated as different products. The `createProduct` duplicate check uses case-insensitive regex, so the API-level check is stricter than the index.

## Backend createProduct duplicate check

**File:** `controller/product.js`

Lines 121-132 add a duplicate check before inserting a new product:

```js
const normalizedName = name.trim().replace(/\s+/g, ' ');
const existing = await Product.findOne({
  name: { $regex: new RegExp(`^${normalizedName.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')}$`, 'i') },
  category: { $regex: new RegExp(`^${category.trim()}$`, 'i') }
});
if (existing) {
  return res.status(409).json({
    success: false,
    error: `Product "${name}" already exists in category "${category}". Use the edit form to update it.`,
    existingProductId: existing._id
  });
}
```

The check normalizes the product name by collapsing multiple spaces into one, then does a case-insensitive regex match on both name and category. If a match is found, the API returns 409 Conflict with the existing product's ID.

The error response includes `existingProductId`, allowing the dashboard to navigate directly to the edit page.

Lines 177-183 catch E11000 errors from the unique index as a fallback.

**Gap:** The normalization happens in the `createProduct` function but not in the Product model's save hook or schema. If a product is created with "Ways 200  Grammes" (double space) via the dashboard, it passes the duplicate check (normalized to "Ways 200 Grammes") but is saved to MongoDB with the double space intact. A subsequent attempt to create "Ways 200 Grammes" (single space) would fail the duplicate check even though the names are technically different in the database. This is a minor edge case — the duplicate check is correct, but the underlying data inconsistency could confuse manual queries or reports. Consider adding a pre-save hook to normalize names.

## Backend seed script idempotency

**File:** `seedProducts.js`

Lines 154-164 improve the duplicate check to include both name and category:

```js
// Normalize name: trim whitespace, collapse multiple spaces
const normalizedName = productName.trim().replace(/\s+/g, ' ');

// Skip if product already exists (by name exact + category)
const existing = await Product.findOne({
  name: { $regex: new RegExp(`^${normalizedName.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")}$`, "i") },
  category: { $regex: new RegExp(`^${catName}$`, "i") }
});
if (existing) {
  console.log(`     ⚠️  Produit existant (skip) : ${normalizedName} in ${catName}`);
  skippedProducts++;
  continue;
}
```

The old logic checked name only. If two products with the same name existed in different categories, the second one was incorrectly skipped. The fix adds category to the check, making it consistent with the unique index and the `createProduct` duplicate check.

## Dashboard duplicate warning

**File:** `dashboard/src/pages/ProductForm.jsx`

Lines 165-189 add a pre-submit duplicate check for new products (not edits):

```js
if (!isEdit) {
  try {
    const { data } = await api.get('/products', {
      params: { name: form.name, category: form.category, limit: 10 }
    })
    const list = Array.isArray(data) ? data : (data?.data ?? [])
    const matches = list.filter(p => 
      p.name.toLowerCase().trim() === form.name.toLowerCase().trim() &&
      p.category.toLowerCase().trim() === form.category.toLowerCase().trim()
    )
    if (matches.length > 0) {
      const confirmed = window.confirm(
        `A product named "${form.name}" already exists in ${form.category}.\n\n` +
        `Do you want to edit the existing product instead?`
      )
      if (confirmed) {
        navigate(`/products/edit/${matches[0]._id}`)
        return
      } else {
        return // User chose to cancel
      }
    }
  } catch (err) {
    console.warn('Duplicate check failed:', err.message)
  }
}
```

The filter on lines 172-175 does a case-insensitive exact match on both name and category, consistent with the backend duplicate check.

**Performance concern (likely):** The check runs on every submit, even if the product name is clearly unique. Consider debouncing the check or caching the result.

The check failure is non-blocking (line 186) — if the API call fails, the form submission proceeds and the backend duplicate check will catch the duplicate.

## Database cleanup script

**File:** `.agents/tasks/cleanup-duplicates.mjs`

The script groups products by case-insensitive (name, category), identifies duplicate groups, keeps the oldest product in each group, and deletes the rest. A backup JSON file is created before deletion.

The script requires `DELETE_CONFIRMED=true` to proceed with deletion (lines 111-117). Without this flag, it runs in dry-run mode.

**Status:** Script exists but was not executed. The diagnostic confirmed 0 duplicates in the database.

**Gap:** The script does not update references in orders, carts, or favorites before deleting duplicate products. If an order contains a reference to a deleted product, the order's product reference becomes invalid. For this deployment, the gap is acceptable because 0 duplicates exist. If the script is used in the future, add a migration step to update foreign-key references before deletion.
