# Full notification system for HookaDrop

This change introduces the complete notification infrastructure for HookaDrop: a Mongoose Notification model and notification service, Firebase Cloud Messaging integration with lazy initialization, seven REST API routes with admin extensions, event hooks wired into orders/products/auth/stripe controllers, an in-app NotificationsActivity with RecyclerView adapter, a ProfileActivity toggle with Android 13+ runtime permission flow, a HomeActivity unread badge, and a dashboard admin page with a broadcast feature. All three FEAT files are marked completed and the build artifacts confirm no compilation errors.

Watch for: (1) **confirmed** — every successful login unconditionally writes a `new_login` security notification to the DB, with no deduplication, so the notification center fills up rapidly for active users; (2) **confirmed** — the broadcast endpoint inserts Notification documents for all users with `notificationsEnabled:true` but without validating the `type` field against the Notification model enum, so a caller passing `type:"order"` will produce documents that render incorrectly in the admin dashboard TypeBadge; (3) **confirmed** — real Stripe test credentials (`sk_test_51UNLss…`) and a Resend API key (`re_hucJuciV_…`) are committed in `.env` — these are pre-existing but should be rotated; (4) **possible** — the `loadServerNotificationPreference()` call in `onResume` re-attaches a new `setOnCheckedChangeListener` that calls `setupNotificationSwitch`, while the original listener in `setupMenuItems` is still also attached, creating two active listeners after the first resume.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The backend foundation is solid: a single Notification collection, lazy FCM initialization that degrades gracefully without credentials, fire-and-forget hooks in all five event sites (createOrder, updateOrderStatus, stripe confirm-payment, stripe webhook, createProduct, login, changePassword), and per-user ownership checks on every mutation endpoint. The admin routes sit in the same file and require `requireRole('admin')`.

The Android client covers the full lifecycle: FCM token registration on sign-in and token refresh, three notification channels, the NotificationsActivity with per-type icon tinting, unread badge on the HomeActivity bell, and a robust permission flow including the Settings deep-link when the user permanently denies. All PATCH calls go through PUT aliases because `ApiClient` has no `patch()` method — the backend dual-registers both verbs for every mutating notification route.

The security notification hook fires on every successful login without any deduplication logic. A user who logs in daily will accumulate one `new_login` record per login, which is accurate but will drown the notification center in security entries within weeks. The original requirement distinguished "new device / unrecognized device" from repeat logins; the implementation fires for every login regardless.

The broadcast endpoint accepts an arbitrary `type` string from the request body and writes it directly to the Notification documents. The Notification schema's `type` field has an enum (`['order','security','product','promo','account']`), so a `type` value outside that set will be rejected by Mongoose at insert time — but the endpoint doesn't pre-validate it and will return a 500 with a non-descriptive error if the caller sends an unlisted type.

The `ProfileActivity.loadServerNotificationPreference()` method removes the original `setOnCheckedChangeListener` and replaces it with a new one pointing at `setupNotificationSwitch`. On subsequent resumes (re-open app, navigate back), both the replacement listener and the original one from `setupMenuItems` could be active depending on execution order, potentially triggering double sync calls.

<summary>Issues (4)</summary>

1. **Login flood in notification center** — `notifySecurityEvent` fires for every successful login with no device fingerprinting or deduplication. A user who logs in repeatedly will accumulate unlimited `new_login` records. Add a recency check (e.g., skip if a `new_login` notification already exists for this user in the last 10 minutes) or implement device tracking to match the original requirement of "new/unrecognized device" semantics.

2. **Broadcast type not validated against enum** — `POST /api/notifications/admin/broadcast` passes the client-supplied `type` directly to `Notification.insertMany`. If `type` is outside `['order','security','product','promo','account']`, Mongoose throws a ValidationError and the endpoint returns 500 with no useful message. Add explicit enum validation on the broadcast handler before the DB insert.

3. **Double listener on ProfileActivity switch after resume** — `loadServerNotificationPreference()` calls `b.switchNotifications.setOnCheckedChangeListener(null)` to remove the listener, then sets a new one to `setupNotificationSwitch`. But the original `setupMenuItems` listener is set during `onCreate` and is not the same reference, so it may persist. After the first `onResume`, any toggle change could fire two listeners. Restructure so a single named listener is set once and updated in-place, or use a flag to suppress programmatic changes.

4. **Real credentials in committed .env** — `STRIPE_SECRET_KEY=sk_test_51UNLss…` and `RESEND_API_KEY=re_hucJuciV_…` are live values in `.env` committed to the repo. While pre-existing and test-tier, they should be rotated and the file added to `.gitignore`. This is not introduced by this PR but is now surfaced by the env additions documented by FEAT-001.

## Login-triggered new_login flood

`controller/user.js` → `Login()` unconditionally calls `notifySecurityEvent(user._id, 'new_login')` via `setImmediate` on every successful authentication. `notifySecurityEvent` does a straight `Notification.create()` with no deduplication guard. There is no device ID, IP address, or recency check. The FEAT-001 spec called for this to fire "new login from a new device" and "login from a device not previously recognized" — the implementation fires for every login. For a user who logs in daily, this generates 365 security notifications per year. The notification center UI shows all of them with no grouping or truncation.

A minimal fix is a recency guard inside `notifySecurityEvent` before the `createNotification` call:

```js
const recent = await Notification.findOne({
  user: userId, type: 'security', title: 'New Login Detected',
  createdAt: { $gte: new Date(Date.now() - 10 * 60 * 1000) }
});
if (recent) return;
```

A more complete fix stores a device fingerprint (user-agent hash + IP) and only fires when a genuinely new fingerprint is seen.

## Broadcast type enum gap

`POST /api/notifications/admin/broadcast` extracts `type` from `req.body` with a default of `'account'`. The value is written to every Notification document via `insertMany`. Mongoose will throw `ValidationError: type: 'whatever' is not a valid enum value` for any type outside the enum, which propagates as a 500. The dashboard's BroadcastTab only offers `account/product/promo` in its select, so client-side this path is constrained — but the backend endpoint makes no such guarantee. A one-line guard before the insert:

```js
const VALID_TYPES = ['order','security','product','promo','account'];
if (!VALID_TYPES.includes(type)) {
  return res.status(400).json({ success: false, message: `Invalid type. Must be one of: ${VALID_TYPES.join(', ')}` });
}
```

## ProfileActivity switch double-listener

In `ProfileActivity.setupMenuItems()`, the switch gets a `setOnCheckedChangeListener` lambda. In `loadServerNotificationPreference()`, after the server responds, the code calls `b.switchNotifications.setOnCheckedChangeListener(null)` and then sets a new listener pointing at `setupNotificationSwitch`. Android's `setOnCheckedChangeListener(null)` removes the *most recently registered* listener. If `setupMenuItems` ran before `loadServerNotificationPreference`, setting null will remove the one set in `loadServerNotificationPreference` from a previous resume cycle — not the original `setupMenuItems` one. After two resumes, there may be two active listeners (confirmed by tracing the call order: `onCreate` → `setupMenuItems` sets L1; `onResume` → `loadServerNotificationPreference` sets null + L2; second `onResume` → sets null (removes L2) + sets L3; L1 is never removed). The safest fix is to make the switch listener a field and assign once:

```kotlin
private var notifSwitchListener: CompoundButton.OnCheckedChangeListener? = null
// in onCreate after setup:
notifSwitchListener = CompoundButton.OnCheckedChangeListener { _, checked -> handleNotifToggle(checked) }
b.switchNotifications.setOnCheckedChangeListener(notifSwitchListener)
// in loadServerNotificationPreference, suppress programmatically:
b.switchNotifications.setOnCheckedChangeListener(null)
b.switchNotifications.isChecked = enabled
b.switchNotifications.setOnCheckedChangeListener(notifSwitchListener)
```

## FCM credential handling

`FCM_SERVICE_ACCOUNT_KEY` and `FIREBASE_PROJECT_ID` are read from `process.env` only. The Android `google-services.json` is a placeholder with all-zero IDs and `PLACEHOLDER_API_KEY_REPLACE_WITH_REAL_KEY` — no real Firebase credentials are in the app source (confirmed). Server starts cleanly without FCM env vars; `initializeFirebase()` logs a warning and returns `false` rather than throwing.
