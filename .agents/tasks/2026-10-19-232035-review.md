# Profile Persistence Fix — Post-Implementation Review

Two commits complete the profile persistence feature: backend fields and endpoint, Android load/save logic, and session sync across all auth flows. The last commit added `saveProfileFromServer` to EmailVerifyActivity, closing the registration gap identified in the previous review.

**Watch for:** Username uniqueness race condition — concurrent updates can both pass the check and create duplicates (likely). Email updates don't sync with external auth providers, causing sign-in failures if Firebase/Auth0 manages authentication (confirmed if external auth is used, otherwise not applicable). Date format accepted as freeform string with no validation, risking parse errors on display (confirmed). Avatar upload disables the Save Changes button, blocking unrelated profile edits during upload (confirmed). ValidationAndSave returns `true` before the async save completes, navigating away while the request is still in flight (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The backend adds firstName, lastName, username, and dateOfBirth to the User schema as optional fields, and a PUT /api/profile/update endpoint behind protectRoute that validates username and email uniqueness before updating. The Android EditProfileActivity loads profile data from GET /api/profile/me on every open, populates fields from the response, and saves changes via PUT /api/profile/update. SessionManager.saveProfileFromServer syncs all fields to SharedPreferences after login (SignInActivity), registration verification (EmailVerifyActivity), and profile updates (EditProfileActivity).

The username uniqueness check queries the database before the update, but the query and write are not atomic. Two concurrent requests for different users can both pass the check and write the same username. Email updates go directly to MongoDB without checking whether the email is managed by an external provider (Firebase, Auth0), which will cause the provider and database to diverge if the user changes their email in the app.

The date of birth is stored as a String with no backend validation. The Android DatePickerDialog formats it as "dd / MM / yyyy", but a user who manually edits the field can enter any string, and the backend accepts it unchanged. The avatar upload function disables the Save Changes button instead of just the avatar UI, blocking unrelated edits during upload. The validateAndSave function returns `true` and navigates away before the coroutine completes, so the user leaves the screen while the API request is still in flight.

<details>
<summary>Issues (5)</summary>

1. **Username uniqueness race condition** — Two users updating their profiles simultaneously can both pass the `User.findOne` check (profileController.js line 142) before either write commits, resulting in duplicate usernames. Add a unique sparse index to the username field in the User schema (`username: { type: String, default: null, unique: true, sparse: true }`), or catch the duplicate key error from findByIdAndUpdate and return a 400 error.

2. **Email update doesn't sync with external auth provider** — If the user's email is managed by Firebase, Auth0, or another provider, updating it in MongoDB (profileController.js line 165) won't update the provider's record. The user will be unable to sign in because the provider still has the old email. Check if the app uses external auth; if so, reject email updates with an error message, or integrate the provider's email-change API.

3. **Date of birth stored as unvalidated string** — The backend accepts any string for dateOfBirth (User.js line 77, profileController.js line 150). The Android DatePickerDialog produces "dd / MM / yyyy", but a user who types directly into the field can save "not a date" or "1999-12-31" or any other format. Future code that parses this field will break. Either validate the format server-side (regex or Date parse check) or change the schema to `dateOfBirth: { type: Date, default: null }` and parse the string before saving.

4. **Avatar upload blocks Save Changes button** — uploadAvatarToBackend disables b.btnSave (EditProfileActivity.kt line 325) during upload. While the photo is uploading, the user cannot save firstName, lastName, username, phone, or dateOfBirth changes. Disable only the avatar UI (`b.avatarEdit.isEnabled = false`) or add a separate progress indicator, and leave b.btnSave functional for unrelated fields.

5. **validateAndSave navigates away before save completes** — validateAndSave returns `true` immediately after launching the coroutine (line 241), and the caller navigates back before the PUT /api/profile/update response arrives. If the network is slow or the request fails after navigation, the user thinks their changes were saved but they were not. Move the `navigateBack()` call inside the coroutine's success block (after line 254), and return `false` from validateAndSave to prevent the caller from navigating.

<summary>Details</summary>

## Registration flow now syncs profile after verification

The previous review flagged that SignUpActivity didn't call saveProfileFromServer. The latest commit added `session.saveProfileFromServer(user)` to EmailVerifyActivity (line 226). The registration payload sends name, email, phone, and age but not firstName, lastName, username, or dateOfBirth — those fields remain null until the user manually opens Edit Profile.

## Username uniqueness check is not atomic

The updateFullProfile controller checks username uniqueness with `User.findOne({ username, _id: { $ne: req.user._id } })` (profileController.js line 142). If the query returns no match, the controller proceeds to `User.findByIdAndUpdate` (line 167). These are two separate database operations.

If two users (A and B) both try to claim the username "newuser" at the same time:
1. User A's request queries for "newuser" — finds nothing, proceeds.
2. User B's request queries for "newuser" — finds nothing, proceeds.
3. User A's write commits.
4. User B's write commits with the same username.

The database now contains two users with username "newuser", violating the intended uniqueness constraint. The solution is a unique index on the username field. Adding `unique: true, sparse: true` to the schema will cause the second write to fail with a duplicate key error, which the controller can catch and return as a 400 error.

## Email update bypasses external auth provider

The email update logic (profileController.js line 160-165) checks that the new email is different from the current email and not already claimed by another user, then writes it to MongoDB. If the user's email is managed by an external authentication provider (Firebase Authentication, Auth0, Okta, AWS Cognito), the provider's user record is not updated.

The next time the user tries to sign in, the provider will still use the old email. If the app validates the JWT's email claim against the database email, the mismatch will cause authentication failures. If the provider overwrites the database email on every sign-in, the user's email change will be lost.

The severity depends on whether the app uses external authentication. If authentication is entirely local (email/password stored in MongoDB and validated by the backend), this finding does not apply. If an external provider manages authentication, this is a blocking issue.

## Date format stored as freeform string

The User schema defines dateOfBirth as `{ type: String, default: null }` (User.js line 77). The Android DatePickerDialog produces "dd / MM / yyyy" (EditProfileActivity.kt line 178), but the backend performs no validation. A user who manually edits the field can type "January 1 2000", "2000-01-01", "not a date", or any other string, and the backend saves it unchanged.

Future code that needs to parse or display the date of birth (age calculation, birthday notifications, filtering) will fail on unexpected formats. The backend should either validate the format with a regex or date parser and reject invalid values, or change the schema to `dateOfBirth: { type: Date, default: null }` and parse the incoming string before saving.

## Avatar upload prevents saving other fields

The uploadAvatarToBackend function sets `b.btnSave.isEnabled = false` and `b.btnSave.text = "Uploading…"` (EditProfileActivity.kt lines 325-326) while uploading the photo. The upload is unrelated to firstName, lastName, username, phone, and dateOfBirth, but the user cannot save changes to those fields until the upload completes.

The fix is to disable only the avatar UI (`b.avatarEdit.isEnabled = false`) and leave the Save Changes button enabled, or add a separate progress indicator on the avatar itself (a circular progress bar overlaying the image).

## Navigation happens before save completes

The validateAndSave function launches a coroutine (line 231) to send PUT /api/profile/update, then immediately returns `true` (line 273). The caller (setupListeners, line 204) checks the return value and calls `navigateBack()` before the API request completes.

The coroutine updates the button state (lines 249-252) and calls `toast("Profile saved successfully")` and `navigateBack()` inside the success block (lines 255-256), but the outer return value already caused the activity to navigate back. If the network is fast, both navigation calls happen in quick succession and the user doesn't notice. If the network is slow, the user sees the Edit Profile screen disappear before the request finishes, and if the request fails, they never see the error message.

The fix is to remove the return statement (line 273) or change it to `return false`, and rely entirely on the coroutine's success/failure blocks to control navigation. The button click handler should not call `navigateBack()` based on the return value.
