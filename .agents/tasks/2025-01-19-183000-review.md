# Popular Products: Favorites, cart images, and sales tracking

This change fixes three distinct problems in the HookaDrop e-commerce Android app: Popular Products items couldn't be added to favorites, products added to cart from Popular Products showed placeholder images instead of actual product photos, and the Popular Products section displayed arbitrary products instead of best-sellers. The fix adds a heart button to product cards with proper wiring to FavoritesManager, updates CartItemAdapter to load remote images using Glide, adds backend `soldCount` tracking with a new `/api/products/popular` endpoint, and updates the Android home screen to fetch from that endpoint.

**Watch for:** The soldCount increment happens at order creation, not payment confirmation (possible), unhandled edge case when backend returns empty popular products list (likely), and missing null safety in cart image loading when imageUrl is malformed (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The heart button was added to `item_product.xml` and wired in ProductAdapter to call FavoritesManager.toggle with a scale animation.

CartItemAdapter now checks for remote products (imageUrl + isRemote flag) before falling back to local drawable resources, using Glide with placeholder and error handling.

The backend Product model gained a soldCount field (default 0), and the order controller increments it by quantity when orders are created. The increment is non-blocking and logged on failure, so orders can still be placed even if soldCount updates fail, but soldCount may be inaccurate.

A new `/api/products/popular` endpoint returns the top 10 products sorted by soldCount descending, placed before the parameterized `:id` route to avoid collision. HomeActivity calls RemoteDataProvider.getPopularProducts() which hits this endpoint with a fallback to static products.

The soldCount increment occurs in createOrder before payment is confirmed—if the app has a payment flow that can fail after order creation, soldCount will count unpaid orders, skewing the popular products ranking toward items frequently abandoned in checkout.

## Favorites button wiring

The drawable uses `#66000000` (40% opacity black), which works on light backgrounds but may have low contrast on dark product images—if visibility becomes an issue, consider adding a white border or increasing opacity.

## Cart image loading priority

CartItemAdapter.onBindViewHolder checks if a product has `imageUrl.isNotEmpty() && isRemote` before attempting to load it with Glide, falling back to `imageRes` for static products, and finally to the `ic_hookah_neon` placeholder if both are missing. The adapter calls `DataProvider.getProductById` to get the freshest product data (in case the cart item's serialized copy is stale).

The code doesn't validate that `imageUrl` is a well-formed URL before passing it to Glide—if the backend returns a relative path or an empty string, Glide will fail silently and show the error drawable. This is acceptable for user experience (they see a placeholder, not a crash) but makes debugging harder.

## Backend soldCount tracking and order creation

The order controller's createOrder function increments soldCount for each product in the order by the quantity ordered, using `Product.findByIdAndUpdate(item.product, { $inc: { soldCount: item.qty } })`. The update is wrapped in a .catch that logs errors but does not block order creation—if the soldCount update fails, the order still succeeds and the customer isn't impacted, but the popular products ranking will be incorrect.

The increment happens immediately after `Order.create(req.body)` succeeds, before payment is confirmed. The Order model has an `isPaid` field (visible in ApiModels.kt), but createOrder doesn't check it before incrementing soldCount. If the app's payment flow allows orders to be created in an unpaid state (e.g., pending payment confirmation), then soldCount will include unpaid orders, which skews the popular products ranking toward items that are frequently added to cart but abandoned before payment.

A safer approach would be to increment soldCount in a payment confirmation webhook (e.g., Stripe or PayPal) or to check `order.isPaid` before incrementing.

## Popular products endpoint and route ordering

The new `/api/products/popular` endpoint is defined in `routes/product.js` before the parameterized `/products/:id` route, which prevents Express from treating "popular" as a product ID.

When all products have soldCount=0 (no orders placed yet), the query returns products sorted by MongoDB's default _id order, which encodes the creation timestamp—so the "popular" products are effectively the oldest products. The endpoint doesn't signal this to the client (e.g., by returning an empty array or a 204 status), so the home screen will display "Popular Products" that aren't actually popular.

A more explicit approach would be to return an empty array when no products have soldCount > 0, or to add a `minSoldCount` filter (e.g., only return products with soldCount >= 1). Alternatively, the endpoint could return a `hasData: false` flag when soldCount is uniformly zero, allowing the Android app to show a different message like "New Arrivals" instead of "Popular Products."

## Android home screen integration

HomeActivity.loadDataFromBackend() was changed to call `RemoteDataProvider.getPopularProducts()` instead of `RemoteDataProvider.getProducts()`. RemoteDataProvider.getPopularProducts() calls `/api/products/popular` and falls back to `DataProvider.products.take(6)` if the network call fails.

The fallback doesn't distinguish between network failure and an empty response from the backend—if the backend returns `success: true, data: []`, the Android code will treat it as a failure and fall back to static products. An empty backend response should probably be respected (show nothing) rather than replaced with static data.
