# HookaDrop Home Page — View All Buttons Redesign

Both top-right "View All" TextViews are replaced with full-width styled buttons below their respective sections, and a new `PopularProductsActivity` screen loads the top-15 popular products. The change spans two commits: the layout/drawable work in FEAT-001 (67179ae) and the activity creation + navigation wiring in FEAT-002 (1a7ae4d). Build succeeded per both FEAT findings fields. The diff is clean: only the four explicitly targeted files (layout, drawables, manifest, HomeActivity) were modified, plus the new activity and layout files added.

Watch for: `CoroutineScope(Dispatchers.Main)` in `loadPopularProducts()` is not tied to the Activity lifecycle — it leaks if the user navigates away before the network call completes (confirmed). No other blocking concerns.

**Verdict**: APPROVED

## High-level view

The layout change is structural: `activity_home.xml` was written from scratch as a new file (the old file didn't exist in git before this branch, confirmed by the diff showing mode `new file`). Both section headers contain only the title `TextView`; the `btnViewAllCategories` and `btnViewAllProducts` `Button` elements appear as siblings of their RecyclerViews in the scroll container, not inside the header `LinearLayout`s.

`PopularProductsActivity` mirrors the pattern of `CategoryProductsActivity`: ViewBinding, `attachBaseContext` with `LocaleManager.wrap`, CartManager listener registered in `onCreate` and removed in `onDestroy`, and a coroutine-based load. The product limit of 15 is enforced client-side via `products.take(15)` after the `getPopularProducts()` call returns. The manifest registers the activity with `exported=false` and the same `Theme.HookahDrop.Main` theme used by all other main-flow screens.

The `btnViewAllProducts` handler in `HomeActivity` was previously calling `goToCategories()`; it now starts `PopularProductsActivity` with the `nav_enter` / `nav_exit` transition. `btnViewAllCategories` continues to call `goToCategories()` unchanged, which is the correct target.

The one lifecycle gap is the bare `CoroutineScope(Dispatchers.Main)` in `loadPopularProducts()`. If the activity is destroyed before the IO call returns, the continuation still runs and touches `b.*` view bindings that no longer exist. The project's other activities (e.g. `CategoryProductsActivity`) use the same pattern, so this is a pre-existing anti-pattern now replicated into the new screen — the new code doesn't make it worse in terms of crash risk (the binding access in the continuation is safe at the object level), but it does constitute a coroutine leak.

<details>
<summary>Issues (1)</summary>

1. **Unscoped coroutine in loadPopularProducts** — `CoroutineScope(Dispatchers.Main).launch { ... }` is not tied to the Activity lifecycle. If the user presses Back before the network call returns, the coroutine keeps running and updates views on an Activity that has been destroyed. Replace with `lifecycleScope.launch { ... }` (already available via `androidx.lifecycle:lifecycle-runtime-ktx`) to get automatic cancellation on `onDestroy`. This is a confirmed leak, though crash risk is low because ViewBinding holds a strong reference until GC.

</details>

### Layout correctness — no residual top-right TextViews

`activity_home.xml` has two section header `LinearLayout`s, each containing exactly one `TextView` (the section title). Neither contains a `TextView` with id `btnViewAllCategories` or `btnViewAllProducts`. Both `Button` elements appear as direct children of the outer vertical `LinearLayout`, positioned after `rvCategories` and `rvProducts` respectively. The IDs, background drawable, text color, chevron drawable, and dimensions match the FEAT-001 spec exactly.

### Coroutine lifecycle gap in PopularProductsActivity

`loadPopularProducts()` creates a fresh scope that is never cancelled:

```kotlin
CoroutineScope(Dispatchers.Main).launch {
    val products = withContext(Dispatchers.IO) {
        RemoteDataProvider.getPopularProducts()
    }
    b.progressBar.visibility = View.GONE   // executed after activity may be destroyed
    ...
}
```

`lifecycleScope` is the right fix. The coroutine is created on `Main`, switches to `IO` for the network call, then switches back to update UI — substituting `lifecycleScope.launch` requires no other changes. The `cartListener` deregistration in `onDestroy` is handled correctly and is not affected.

### Navigation wiring

`HomeActivity.btnViewAllProducts` click handler diff (confirmed):

```
-        b.btnViewAllProducts.setOnClickListener { goToCategories() }
+        b.btnViewAllProducts.setOnClickListener {
+            startActivity(Intent(this, PopularProductsActivity::class.java))
+            overridePendingTransition(R.anim.nav_enter, R.anim.nav_exit)
+        }
```

`btnViewAllCategories` continues to call `goToCategories()`. Both wired correctly.
