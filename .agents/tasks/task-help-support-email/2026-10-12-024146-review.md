# Help & Support email submission

The feature replaces a fake 900 ms delay in `HelpSupportActivity.kt` with a real `POST /api/support` API call, backed by a new Express controller that sends an admin notification to `hookadrop@gmail.com` and a confirmation email to the user. The backend route is protected by `protectRoute`, so user identity comes from the verified JWT rather than the request body. The admin email is awaited (critical path); the user confirmation is fire-and-forget with a `.catch()` logger. Both `FEAT-001` (backend) and `FEAT-002` (Android) report `"status": "completed"` with build verification.

Watch for: `EMAIL_PASSWORD` in `.env` is still the placeholder `"your_app_password_here"` — emails will silently fail until a real Gmail App Password is set. The `USE_LOCAL = true` flag in `ApiClient.kt` points to the emulator URL (`http://10.0.2.2:8000`), which will fail on a real device; this is a known dev config but must be switched before production.

**Verdict**: APPROVED

---

## High-level view

The backend is correctly structured as an ES module route + controller pair, mounted at `/api/support` in `server.js`. `protectRoute` gates the endpoint and populates `req.user`; the controller reads `req.user.name` and `req.user.email`, both confirmed against the User model (the schema field is `name` — the fallback chain `fullname || name || username` reaches it safely).

`mailSender` is awaited for the admin notification so a Nodemailer failure surfaces as a 500; the user confirmation is fire-and-forget, appropriate since the admin email is the operationally critical path. Input validation on the backend (empty subject, category index 0, description < 20 chars) mirrors the Android-side checks, so the 400 path is reachable from both sides.

The Android change is isolated to `setupSubmit()`. `lifecycleScope.launch` bounds the coroutine to the activity lifecycle, and `ApiClient.post` dispatches to `Dispatchers.IO` — consistent with the rest of the codebase.

`subject`, `category`, `description`, and `orderNumber` are interpolated into the admin HTML email without HTML-escaping. The email goes only to the operator's inbox, so the blast radius is limited — but a malicious user could embed HTML that renders in the admin's email client.

The one real operational gap is `EMAIL_PASSWORD`. The `.env` placeholder means no email will actually deliver, and because there is no database persistence, a failed delivery means the request is permanently lost with no fallback audit trail.

### XSS in admin email HTML

`subject`, `category`, `description`, and `orderNumber` from `req.body` are interpolated directly into the admin email HTML string (e.g., `<td ...>${subject}</td>`) without HTML-escaping. A user submitting `<script>alert(1)</script>` as a subject would have that string land verbatim inside a `<td>` in the operator's inbox. Most modern email clients strip `<script>` tags, but other payloads (inline event handlers, CSS injection) may render. The risk is bounded to the operator's inbox — no external users receive this email — but it is still confirmed user-controlled input in an HTML context.

The user confirmation email interpolates `${subject}` and `${userName}` (`req.user.name` from the database). `userName` is not attacker-controlled at submission time, but `subject` is.

A minimal fix:

```js
const esc = (s) => String(s ?? "").replace(/&/g,"&amp;").replace(/</g,"&lt;").replace(/>/g,"&gt;").replace(/"/g,"&quot;");
// then: ${esc(subject)}, ${esc(description)}, etc.
```

### `req.user` field fallback chain

The User model declares the field as `name`. The controller reads `req.user.fullname || req.user.name || req.user.username || "Unknown"`. `fullname` and `username` are not fields on the schema — they will always be `undefined`, so the expression always resolves to `req.user.name`. This is harmless but noisy; trimming to `req.user.name || "Unknown"` would be clearer.

</details>
