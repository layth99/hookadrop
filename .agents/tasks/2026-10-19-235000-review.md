# Profile Persistence Fix — Review Pass 2

Backend adds profile fields to User schema and a PUT /api/profile/update endpoint with username/email uniqueness checks. Android EditProfileActivity fetches from GET /api/profile/me on load and saves via PUT /api/profile/update. SessionManager syncs all fields across sign-in, registration, and profile edits.

**Watch for:** validateAndSave returns true before async save completes, causing premature navigation (confirmed). Email updates bypass external auth providers if Firebase/Auth0 manages authentication (confirmed if external auth is used). Username uniqueness check is not atomic, allowing duplicate usernames under concurrent load (likely). Date of birth accepts freeform strings with no validation (confirmed). Avatar upload disables Save Changes button, blocking unrelated edits (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The implementation adds firstName, lastName, username, and dateOfBirth fields to the User model as optional strings, and a PUT /api/profile/update controller that checks username and email uniqueness before updating. EditProfileActivity loads profile data on open from GET /api/profile/me, populates form fields, and saves changes via PUT with validation. SessionManager.saveProfileFromServer syncs all fields to SharedPreferences after login, registration verification, and profile updates. A default avatar drawable (bg_avatar_default.xml) provides a themed circular fallback.

The critical issue is that validateAndSave launches a coroutine to send the PUT request, then immediately returns true, allowing the button click handler to navigate away before the API call completes. On slow networks, the user leaves the screen while the request is in flight, and if it fails, they never see the error. The coroutine's navigateBack() call inside the success block fires after the caller already navigated, causing no visible harm but indicating the flow is broken.

The username uniqueness check queries the database, then writes if no match is found, but these are separate operations. Two concurrent requests can both pass the check before either write commits, creating duplicate usernames. The email update writes directly to MongoDB without syncing with external authentication providers (Firebase, Auth0), which will break sign-in if the provider manages the email. The date of birth is stored as an unvalidated string, accepting any format the user types, which will break future parsing logic.

## Async save returns true before completion

The validateAndSave function (EditProfileActivity.kt line 197) validates input, launches a coroutine to send PUT /api/profile/update (line 231), and returns `true` on line 273. The button click handler (line 193-196) checks the return value, toasts "Profile saved successfully", and calls navigateBack().

The coroutine sends the PUT request on Dispatchers.IO (line 245), waits for the response, and if successful, toasts success and calls navigateBack() (lines 255-256). The problem is that the outer return statement executes immediately after launching the coroutine, before the response arrives. The click handler's toast and navigateBack() fire first. If the network is fast, the coroutine's navigateBack() fires a moment later, causing no visible issue. If the network is slow, the user leaves the screen before the request completes, and if the request fails (lines 258-260), the error toast never reaches the user because the activity is already gone.

The fix: remove the `return true` statement on line 273 (or change it to `return false`), remove the toast and navigateBack from the click handler (lines 194-195), and rely entirely on the coroutine's success/failure blocks to control navigation. The button should launch the async save and do nothing else. The coroutine handles all UI feedback and navigation.

## Email updates bypass external authentication providers

The updateFullProfile controller (profileController.js line 138) checks if the new email is different from the current email and not claimed by another user (lines 160-163), then writes it to MongoDB (line 167). If the app uses an external authentication provider (Firebase Authentication, Auth0, AWS Cognito, Okta), the provider's user record is not updated.

When the user next signs in, the provider will authenticate them with the old email. If the backend validates the JWT's email claim against the database, the mismatch will cause authentication failures. If the provider's email overwrites the database email on every sign-in (via saveProfileFromServer in SignInActivity), the user's email change will be silently lost.

This finding applies only if external authentication is used. If the app handles authentication entirely locally (email/password stored in MongoDB, validated by the backend), this is not an issue. The severity is HIGH if external auth is used, and NOT_APPLICABLE if auth is local. The task description mentions Firebase, suggesting external auth is active.

The fix: check how authentication works (is there Firebase configuration in the Android app? Is the JWT issued by Firebase or by the backend?). If external auth is used, either reject email updates with a 400 error and a message like "Email managed by authentication provider. Contact support to change your email," or integrate the provider's email-update API and update both the provider and MongoDB atomically.

## Username uniqueness check is not atomic

The updateFullProfile controller checks username uniqueness with `User.findOne({ username, _id: { $ne: req.user._id } })` (line 142). If no match is found, the controller proceeds to `User.findByIdAndUpdate` (line 167). These are two separate database operations.

If two users (A and B) both try to claim the username "newuser" at the same time:
1. User A's request queries for "newuser" — finds nothing.
2. User B's request queries for "newuser" — finds nothing (A's write hasn't committed yet).
3. User A's findByIdAndUpdate commits, setting their username to "newuser".
4. User B's findByIdAndUpdate commits, setting their username to "newuser".

Both users now have the same username, violating the intended uniqueness constraint. The likelihood depends on traffic volume; under low load, this is rare. Under moderate load, it's plausible.

The fix: add `unique: true, sparse: true` to the username field in the User schema (User.js line 77). The sparse option allows multiple null values (for users who haven't set a username yet) but enforces uniqueness for non-null values. When findByIdAndUpdate tries to write a duplicate username, MongoDB will throw a duplicate key error (code 11000). Catch this error in the controller and return `res.status(400).json({ message: "Username already taken" })`.

## Date of birth accepts any string

The User schema defines dateOfBirth as `{ type: String, default: null }` (User.js line 77). The updateFullProfile controller accepts the incoming dateOfBirth without validation (profileController.js line 150). The Android DatePickerDialog formats the date as "dd / MM / yyyy" (EditProfileActivity.kt line 178), but if the user manually edits the field or a future feature allows keyboard entry, they can type "not a date", "1999-12-31", "January 1 2000", or any other string, and the backend saves it unchanged.

Future code that needs to parse the date of birth (age calculation, birthday notifications, filtering by age range) will fail on unexpected formats. The backend has no way to know which format a given string uses.

The fix: add server-side validation in updateFullProfile. Check that dateOfBirth matches the expected format "dd / MM / yyyy" using a regex like `/^\d{2} \/ \d{2} \/ \d{4}$/` and optionally validate that the date is real (not "99 / 99 / 9999"). If validation fails, return `res.status(400).json({ message: "Invalid date format. Use dd / MM / yyyy" })`. Alternatively, change the schema to `dateOfBirth: { type: Date, default: null }` and parse the incoming string into a Date object before saving, returning a 400 error if parsing fails.

## Avatar upload prevents saving other fields

The uploadAvatarToBackend function (EditProfileActivity.kt line 310) sets `b.btnSave.isEnabled = false` and `b.btnSave.text = "Uploading…"` (lines 325-326) while uploading the photo to Cloudinary. The upload typically takes 1-3 seconds, during which the Save Changes button is disabled.

If the user edits their firstName, lastName, username, phone, or dateOfBirth, then taps the camera icon to upload a new avatar, they cannot tap Save Changes to save the text field changes until the upload completes. The avatar and the text fields are unrelated; disabling the Save Changes button blocks unrelated work.

The fix: disable only the avatar UI during upload. Set `b.avatarEdit.isEnabled = false` (or `b.ivCameraIcon.isEnabled = false` if that's the clickable view) and leave `b.btnSave` enabled. Alternatively, add a small progress indicator (a circular progress bar overlaying the avatar image) to show the upload is in progress, and leave both the avatar UI and the Save Changes button enabled. The user can save text field changes while the avatar uploads in the background.
